# project-workflow

**把一个「规则 / 状态 / 证据」三分的工作流，装进一个项目 —— 新建的或已有的。**

这是一个 Agent Skill（`SKILL.md` + `references/` + `templates/`），
不是库、不是 CLI，没有依赖、没有构建步骤。

---

## 它解决什么

项目里最常见的一种慢性病：**同一类错误反复出现，而每次都被当成"这次是意外"。**

这套工作流的作用是给它一个出口 —— **犯错之后有地方记**，
下次开工前有人（或代理）会读到。

**它不承诺不犯错。** 它的内容**全部来自已经犯过的错**。

---

## 四条判断

文件结构只是载体。**这四条才是内容：**

```
1. 规则与状态分开写              否则必然漂移
2. "完成"必须附别人能复现的证据
3. 同一个错误犯两次，就把它变成规则
4. 先怀疑测量方法，再怀疑被测对象
```

---

## 两种模式

| 项目状态 | 模式 | 关键纪律 |
|---|---|---|
| 空目录 / 新项目 | **新建** | 只生成**骨架**，不搬别的项目的坑 |
| 已有历史 | **进行中** | **先探测、先报告、不要动任何文件** |

进行中模式的核心不是补文件，而是**从 git history 里挖出重复的错误模式** ——
详见 `references/archaeology.md`。

---

## 怎么让它生效

把**整个目录**放进一个用户级 skill 根：

```
$DSH_HOME\skills\project-workflow        ← DSH_HOME 被设置时，只有这个生效
<用户主目录>/.agents/skills/project-workflow   ← 设置与否都生效
```

**`~/.dsh/skills` 在 `DSH_HOME` 被设置时不会被扫描** —— 放那里等于没放。

> 更稳的做法：把本仓库 **junction / symlink** 到那个根，
> 这样仓库是唯一来源、不会出现两份互相漂移的副本。

```powershell
# 目录 junction，Windows 上不需要管理员
New-Item -ItemType Junction -Path "$HOME\.agents\skills\project-workflow" -Target "<本仓库路径>"
```

**验证方式**：放好之后，**可用 skill 列表会立即刷新**。
如果它没出现，**先检查根目录，不要先怀疑文件格式**。

## 目录结构

```

  archaeology.md          从 git history 挖重复模式的具体命令

  WORKFLOW.md             协作骨架

```

## 多 agent / 多人协作

**同一个项目常由不同的 agent 接手。出问题的地方通常不是能力，是信息不同步。**

四条规则（详见 `references/multi-agent.md`）：

1. **`进行中` 的条目必须写「谁在做 · 下一步 · 已改动哪些文件」** —— 光写"进行中"等于没写
2. **做完一段就提交，哪怕功能没完成**（`wip:` 前缀）——
   **未提交的工作，对其他 agent 等于不存在**
3. **动手前先 `git status`** —— 工作区脏就停下来读 diff，不要 `stash`、不要"顺手清理"
4. **一个工作区同一时间只允许一个 agent** —— 要并行就用 branch / worktree 隔离

> 第 2 条来自一个真实案例：一次会话做完了一整套十项测试**却没有提交**，
> 八天后另一次会话从 `BACKLOG` 上完全看不出它存在，**差一点重做一遍**。

---

## 故意没做的

- **没有 `scripts/`** —— 这套工作流不需要自动化。**判断不能外包给脚本。**
- **没有把某个项目的具体坑写进来** —— 那些属于那个项目。
  搬过来会**用无关的噪声淹没真正的规则**，见 `references/boundaries.md`。
- **没有"一键生成全部文档"** —— 生成之前必须先问三个问题（`SKILL.md` §2.1），
  答不出就不该写文件。

---

## 来源

来自一个真实项目的三个月实践：那份 `AGENTS.md` 里**每一条规则都对应一次真实事故**。
本仓库保留的是**方法与格式**，不是那个项目的内容。
