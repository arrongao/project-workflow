# 需求池 / BACKLOG

> **本文档只写「状态」，不写「规则」。** 规则在 `AGENTS.md`。
>
> **状态会过期。** 而它是下一个人（或下一个你）**唯一的现实依据** ——
> 过期状态会让人确信地去做**已经做完的事**。
>
> **所以：做完一件事，就顺手改它那一行。**

---

## 一、状态定义

> 状态的含义必须**写死**，否则每个人理解的"完成"都不一样。

| 状态 | 含义 | 谁能改到它 |
|---|---|---|
| `待确认` | 需求本身还没定，或方案未决 | 任何人 |
| `已确认` | 需求已定，可以开工 | 提需求的人 |
| `进行中` | 正在做 | 实现者 |
| `已完成` | **开发完成，已附可复现证据，等待验收** | 实现者 |
| `已通过验收` | 验收通过 —— **只有提需求的人能宣布** | **提需求的人** |
| **`未通过验收`** | **验收不通过，待返工（回到 `进行中`）** | **提需求的人** |
| `已否决` | 明确不做（**写清为什么**，避免重复提议） | 提需求的人 |
| `废弃` | 曾经要做，后来不需要了 | 任何人 |

> ⚠️ **`已完成` ≠ `已通过验收`。** 混用这两个状态，是这个表最常见的失效方式。
>
> ⚠️ **`未通过验收` 不是失败，是信息。** 用它时**写清具体哪里不满足** ——
> 大多数时候是**需求没写清**，那就顺手把需求补清 ✓（见 `WORKFLOW.md`）。
>
> **不要把 `未通过验收` 和 `已否决` 混起来** ✗：前者是"要重做" ✓ 后者是"不做了" ✓。

### ⚠️ `进行中` 的条目必须写三样（多 agent / 多人协作的关键）

**光写「进行中」等于没写** —— 读的人不知道是"刚开工"还是"快做完了"，
也不知道**能不能碰**。

```diff
- | R-002 | 进行中 | 加导出功能 | |
+ | R-002 | 进行中 | 加导出功能 |
+   做的人: <谁> · 开始: <日期> · 下一步: <一个具体的动作> ·
+   已改: <文件>（尚未提交） |
```

| 写什么 | 为什么 |
|---|---|
| **做的人** | 别人知道**该不该碰**、**去问谁** |
| **下一步** | **交接的核心** —— 接手的人照它做就能继续 |
| **已改动 / 未提交的文件** | 否则接手的人不知道工作区为什么是脏的 |

> **未提交的工作，对其他 agent 等于不存在。**
> 做完一段就提交，哪怕功能没完成（`wip:` 前缀）——
> **"等做完再一起提交"是协作里最贵的习惯。**

详见 skill 的 `references/multi-agent.md`。

## 五、怎么维护这张表

1. **新增需求时**：编号顺延，状态一律先写 `待确认`，除非提需求的人已经明确。
2. **开工时**：改成 `进行中`。
3. **完工时**：改成 `已完成`，**并把证据写进备注** —— 命令、输出、截图在哪里。
4. **验收后**：由提需求的人改成 `已通过验收`。
5. **不确定的删除**：先标 `待确认` 并提问，**不要直接删** ——
   "看起来没人用" ≠ "没人用"。

### ⚠️ 不要在这一栏里堆规则

如果你发现自己在写"我们应该总是……"，**那句话属于 `AGENTS.md`**。
