# 协作与验收

<!-- 生成时按项目授权适配；已有流程则链接复用。 -->

## 角色与授权

需求/设计确认人、实现者、验收人：根据用户上下文填写。实现者不得自行产生验收批准；可以按授权负责人的明确结论记录结果。

**决定与记录是两件事**：验收通过、否决、废弃由授权负责人判断；负责人结论明确后，Agent 可以代记账（改状态列、写验收记录）。「结论明确」指负责人在验收记录里写了结论，或在对话中明确表态。没有明确结论时不动状态。

## 状态定义

按项目实际情况裁剪，但必须标明**每个状态由谁决定**：

| 状态 | 含义 | 谁决定 |
|---|---|---|
| 待确认 | 已提出，未决定做不做 | 负责人 |
| 已确认 | 确定要做，未开始 | 负责人 |
| 进行中 | 正在做 | 实现者 |
| 待验收 | 开发完成，等待验收——**不是终点** | 实现者 |
| 已验收 | 负责人确认达标——**唯一终点** | 负责人 |
| 验收未通过 | 不达标，待返工；原因保留在条目里不删 | 负责人 |
| 已否决 | 提议阶段即被否，从未开工 | 负责人 |
| 废弃 | 曾经确认或已实现，后因需求变化不再需要 | 负责人 |

要点：

- **「待验收」不等于「已验收」**。把它当终点会让下个会话以为仍需催办。
- **「已否决」与「废弃」按是否曾经确认过区分**，两者都必须写原因，否则后续会重复提议。
- **废弃可能产生清理工作**：已实现的部分需要一并移除，并记成一条新条目，不要假装没发生。

## 状态一致性

验收结论与状态列记录的是同一件事，靠人工同步**必然漂移**——验收记录写了「通过」，状态列仍停在「待验收」，后续会话就会重复催办。

因此：负责人的结论一旦明确，Agent 在**同一次操作中**同时更新状态列与验收记录，不留中间态。若负责人希望某状态暂不生效，由负责人明确说明。

## 完成条件

交付满足约定范围，完成与风险相称的检查，记录版本、环境、操作或命令、关键结果、未验证范围。实际结果可链接日志，无需复制大量原始输出；敏感数据须脱敏。

文档工作检查来源和一致性；代码工作检查相关行为。构建通过不等于运行验收；删除旧路径前检查配置、动态入口和外部依赖，兼容保留应记录原因及退出条件。

## 文件职责边界

按**是否随时间失效**划分，避免同一事实写在多处：

| 文件 | 放什么 | 不放什么 |
|---|---|---|
| `WORKFLOW.md`（本文） | 协作规则、状态定义、验收标准 | 具体需求、项目进度 |
| `BACKLOG.md` | 需求条目、状态、验收记录、当前焦点 | 规则（只保留状态图例） |
| `AGENTS.md` | 操作规则：构建、约束、已知陷阱 | 任何会随时间变化的状态 |

**判断标准**：会随时间变化的是**状态**；明年仍成立的是**规则**。按此判断放在哪，不以「放一起方便」为由重复。

## 状态与交接

更新唯一任务入口，区分待验收与已验收。未完成时记录负责人、已改文件、提交情况、验证及下一步。是否提交或保留未提交状态依项目约定和用户授权，不自动推送。
