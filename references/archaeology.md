# 考古：从 git history 里挖重复的错误模式

**这是「进行中模式」的核心价值。**
对已有历史的项目，最有用的事情不是补文件，而是**帮它回顾它已经犯过的重复错误**。

**因为**: 一个项目通常已经知道自己的痛，只是**没有把它写下来** ——
于是同一个坑会换一个地方再踩一次。

---

## 〇、先确认：这个项目有得挖吗？

```bash
git log --oneline | wc -l
```

| 提交数 | 该做什么 |
|---|---|
| **1–2 个**（例如只有一个 `init`） | **不要考古** ✗ —— 重复至少需要两次 ✓。明确说"历史太短"，转去做下面 §零之二 |
| 10 个以上 | 可以按 §一～§五 挖 |
| 50 个以上 | 值得做一次完整的考古 |

**硬凑模式比不挖更糟** ✗ —— 那会让项目收到一堆**假规则**，
而假规则会稀释真规则的可信度（`boundaries.md` 第四节）。

## 〇之二、但**任何项目**都能做的一件事：对照文档与现实

**这一条不需要长历史** ✓✓ —— **第一天就可能撞到** ✓。

```bash
git status                 # 工作区干不干净
git log -1 --format='%h %s %ad' --date=short
# 然后：把项目里每个文档都打开，看它说的和上面这两条对不对得上
```

**找这几类不一致**：

- 文档说"未创建提交"，而提交早就有了 ✓（**真实发生过一次，就在一个只有 1 个提交的项目上**）
- 文档说"未实现"，而代码里已经有了
- 文档说"已验证"，而找不到任何验证记录
- README 里的命令**实际跑不起来**

**为什么这类最容易命中** ✓：**状态在 A 文件、证据在 B 文件，而两个文件互相不引用** ✓ ——
**这不是"谁偷懒"，是结构上没有链接** ✓。

**发现之后不要只改那一个字** ✗✓ —— **问一句"为什么会漂移"**，
答案通常就是一条该写的规则 ✓，或者一处该加的交叉引用 ✓。
（§三「找状态与现实的漂移」里还有更多命令。）

---

## 一、准备：先看全貌

```bash
# 全局节奏：提交密度、时间跨度、作者数
git log --oneline | measure            # PowerShell
git log --oneline | wc -l              # bash
git log --format='%ad' --date=short | sort | uniq -c | tail -30

# 提交信息的"意图分布"—— 看它怎么描述自己的改动
git log --format='%s' -n 200 | sed 's/[:(].*//' | sort | uniq -c | sort -rn | head -20
```

**意图分布**一眼能看出项目的性质：如果 `fix:` 占了一半，它处于"打补丁期"；
如果全是 `feat:`，它可能**还没开始还债**。

---

## 二、找"同一个地方被修了两次以上"

### 2.1 同一批文件反复出现在修复提交里

```bash
# 哪些文件最常被 fix: 提交碰到
git log --format='%H %s' -n 500 | grep -i '^[0-9a-f]* *\(fix\|修复\)' | awk '{print $1}' |
  while read h; do git show --name-only --format= $h; done | sort | uniq -c | sort -rn | head -15
```

**一个文件出现在 5 个不同的修复提交里** = 一个模式，不是五次意外。

### 2.2 同一段代码的反复调整

```bash
# 某文件的改动历史，只看提交标题
git log --oneline --follow -- path/to/file

# 一眼看出"改了又改回去"的迹象
git log --oneline --all -- path/to/file | head -30
```

**典型的模式信号**：
- 标题里反复出现同一类词（`layout` / `encoding` / `timeout` / `null` / `race`）
- 同一个函数名在不同提交里被改
- 出现 `revert` / `回退` / `再次修复` / `又` / `again`

### 2.3 用 pickaxe 找"同一个东西被删了又加"

```bash
git log -S'someSymbol' --oneline     # 内容里出现/消失过该符号的所有提交
git log -G'regex' --oneline          # 正则版
```

## 三、找"状态与现实的漂移"

**这是最有价值的一类 —— 因为它直接影响可信度。**

```bash
# 文档说的和代码做的对不上：找"文档说未完成"关键词
grep -rn '待办\|TODO\|待确认\|未实现\|尚未' --include='*.md' .

# 然后逐个核实：那些条目对应的代码，是不是已经存在了？
```

**已见过的真实形状**：
- 需求表里一条标着"进行中"，而它的实现在**三个月前**就提交了
- 变更日志里一条已经发布，而它对应的代码**从没写进那个版本**
- 手册里一条写着"当前有 N 个待清理项"，而它们早清完了

**每找到一个，就问一句**：**「为什么会漂移？是流程缺了哪一步？」**
答案通常就是一条该写进手册的规则（最常见的是：「做完就顺手改状态」）。

---

## 四、找"看起来对但其实不对的验证方式"

在提交信息和代码注释里找**被推翻的结论**：

```bash
git log -p -n 300 | grep -i -B2 -A2 'actually\|其实是\|并不是\|误判\|wrong\|以为'
```

**这类痕迹极有价值** —— 它们记录的是**探针坏了，而不是被测对象坏了**的时刻。
每一条都是「先怀疑测量方法」那条判断的实证。

**收集它们**，因为**只写规则不写案例，规则会被删掉** ——
下一个人看不到代价，就会把那条"多余的谨慎"优化掉。

---

## 五、输出：**只写你确证的模式，一次只加一条**

对每个模式，产出一个**三行卡片**：

```markdown
- **规则**：<祈使句>
  **怎么发现的**：<哪次事故、什么表现、什么代价>
  **为什么不能删掉它**：<如果不写清，下一个人会怎么"优化"掉它>
```

**然后**：
- **只写确证的模式** —— 有两次以上证据的
- **一次只提议一条** —— 不要一次丢十个给使用者
- **展示证据**：把 `git log` 的输出贴出来，让他自己判断这是不是模式
- **等确认**，再写进文件

---

## 六、⚠️ 两条自律

1. **不要用 git history 给人下结论。** 你看到的是**代码的历史**，
   不是**人的意图**。提"这个文件改了很多次"，不要说"你写得有问题"。
2. **提交信息可能不准确。** 一条 `fix: minor` 可能是个大改。
   有疑问就**读 diff**，不要只读标题。

---

## 七、什么时候该停

**当挖出来的模式不再重复，就该停了。**

**目标不是"找出一堆问题"，是"让项目以后少踩一个坑"。**
一个项目一次能吸收的规则是有限的 —— **贪多会把手册变成噪声，反而降低遵守率。**
