# 边界：什么不该做

**这一节比"该做什么"更重要。** 这套工作流最常见的失败方式不是做得太少，而是**做得太多**。

---

## 一、⚠️ 不要搬别的项目的坑

**这是最严重、也最容易犯的一个。**

一个用了很久的项目，它的规则手册里会积累几十条"已知陷阱"。**它们几乎全是那个项目专属的**：

| 看起来像"通用经验" | 实际是 |
|---|---|
| 「某个 API 传空缓冲区返回 `CR_BUFFER_SMALL`，那是成功不是失败」 | **那一个 Windows API** 的行为 |
| 「自绘控件不设背景色会露出一圈灰框」 | **那一个 UI 框架**的行为 |
| 「含非 ASCII 的 `.ps1` 必须写 BOM」 | **那一个 shell 版本**的行为 |
| 「注册表写入在打包应用里会被虚拟化」 | **那一种分发渠道**的行为 |

**把它们搬进新项目 = 用无关的噪声淹没真正的规则。**

### 怎么判断一条规则能不能带走

问：**「这条规则，是在描述一个【方法】，还是在描述一个【平台的事实】？」**

| 是方法 | 是平台事实 |
|---|---|
| 「先证明你的过滤器能匹配到已知存在的样本」 | 「`CM_Get_DevNode_Property` 的空缓冲区返回值是成功」 |
| 「状态和规则分开写」 | 「托盘图标的提升项按 exe 路径存储」 |
| ✅ **可以带走** | ❌ **留在原项目** |

### 唯一该带走的是**格式**

带上「**已知陷阱**这个小节长什么样、每条要写哪三样东西」，
**不要带上小节里的内容**。

---

## 二、不要预先写满假想的规则

**`AGENTS.md` 的第一版应该只有一页。**

一个塞满"可能会踩的坑"的手册：
- 没人读得完 → **被忽略**
- 混着真规则和猜测 → **猜错了会连真的那条一起被不信任**
- 每加一条假规则，就稀释一条真规则的权重

**它是长出来的，不是一次写完的。**

---

## 三、不要覆盖已有内容

**对进行中的项目，默认动作是「提议 + 提问」。**

- 已有 `README` 但很长？→ **指出**它现在承担了几个角色，**问**要不要拆
- 已有 issue 表但状态定义不清？→ **指出**，**问**要不要补状态定义
- **绝不**：改写、移动、删除、重命名它已有的文档

**一个项目可能已有自己的约定 —— 而它可能比这套工作流更适合它。**

---

## 四、不要让占位值看起来像真值

**这一条有两次独立事故作证，每次的代价都是"功能静默错误"。**

| ❌ 错的占位值 | 后果 |
|---|---|
| 版本号写 `1.0.0` | 普通构建产出的程序声称1.0.0，正式包声称另一个版本，**两边互相矛盾而没人发现** |
| 打包脚本的默认身份写成一个**像真标识的字符串** | 本地安装**必然失败**，而且错误码完全指不到根因 |
| `BACKLOG.md` 的示例条目写成 `R-001 登录页改版` | 下一个人**以为那是真需求**，去做了 |

**正确做法**：

```
版本号    →  0.0.0-local
身份      →  <YOUR-ID> / TODO
示例条目  →  R-001 | 待确认 | <你的第一个需求>
```

**占位值必须"一眼看出是占位"。** 如果一个占位值需要**核对**才能确认它是占位，
它就已经是事故的种子了。

**推论（这条也适用于本 skill）**：`templates/` 里的 `<尖括号>` 必须被替换或删掉，
**不要留在成品里**。

---

## 五、不要承诺"用了就不犯错"

**这套工作流只保证一件事：犯错之后有地方记。**

它不保证：
- ❌ 不犯错 —— 恰恰相反，**它的内容全部来自已经犯过的错**
- ❌ 换个人也生效 —— **一个不被遵守的手册不会自动生效**
- ❌ 样本普适 —— 它可能只在**某些类型的项目**上验证过

**如实说明它的来源和局限**，比包装它更有用。

---

## 六、不要把本 skill 的示例当成需求

`SKILL.md`、`references/`、`templates/` 里出现的任何具体条目
（某个状态名、某条规则、某个文件名）**都是例证或占位**。

**要的是方法与格式，不是内容。**

---

## 七、一条元规则

**这套工作流本身也可能错。**

如果它在新项目里**制造了负担而没有减少混乱** —— 那就是它错了，不是项目错了。

**简化它，或者不用它。** 把它当成工具，不要当成教条。
