# 多 agent / 多人协作：信息怎么同步

**一个项目被多个 agent（或多人）接手时，出问题的地方不是能力，是"信息不同步"。**

这份文件只解决一个问题：**让接手的人一眼看出"现在是什么状况、我该从哪接"。**

---

## 一、先说清：什么机制真的能同步

| 机制 | 同步什么 | 可靠性 |
|---|---|---|
| **git 提交** | 已发生的事实 | ★★★ **唯一不会被忘记的通道** |
| `BACKLOG.md` 的状态列 | 需求到哪一步了 | ★★ 靠人手动写 ✓ 会漏 |
| `AGENTS.md` | 踩过的坑（规则） | ★★ 只写"犯过两次"的 |
| 代码注释 | 为什么这么写 | ★ 容易被覆盖 |
| 口头 / 聊天约定 | 任何东西 | ☆ **一定会忘** |

> **推论**：**没有提交的工作，对其他 agent 等于不存在。**
> 这条比它看起来重要得多 —— 见 §五的真实案例。

---

## 二、四条规则

### 规则 1：`进行中` 的条目**必须写归属和下一步**

**光写"进行中"等于没写** —— 读的人不知道是"刚开工"还是"快做完了"，
也不知道**能不能碰**。

```diff
- | R-008 | 进行中 | 全局异常处理 | 无（已真实发生过一次静默崩溃） |
+ | R-008 | 进行中 | 全局异常处理 |
+   做的人: <谁> · 开始: 2026-10-05 · 下一步: 跑一遍十项测试 ·
+   已改: CrashGuard.cs / windows/tests/（尚未提交） |
```

**三样缺一不可**：

| 写什么 | 为什么 |
|---|---|
| **做的人** | 另一个 agent 才知道**该不该碰**，以及**去问谁** |
| **下一步** | 这是**交接的核心** —— 接手的人照它做就能继续 ✓ |
| **已改动的文件**（尤其是未提交的） | 否则接手的人**不知道工作区为什么是脏的** |

### 规则 2：**做完一段就提交，哪怕功能没完成**

```
wip: 十项测试写完了，还没跑通

- CrashGuardTests 立起来了，编译通过
- 跑起来有 3 项失败，明天查
```

**理由**：文件会被漏看 ✓ 注释会被覆盖 ✓ 聊天会忘 ✓ —— **提交不会** ✓✓

**"等做完了再一起提交"是跨 agent 协作里最贵的一个习惯** ✗ ——
因为它让**中间状态完全不可见**，而这正是别人最需要的信息。

> **未提交 ≠ 未完成。** 把这两件事混起来，就会一直不提交。

### 规则 3：**动手前的第一个动作是看工作区**

```bash
git status        # 不干净 ⇒ 有人做到一半
git log -5        # 最近发生了什么
```

**工作区不干净时的正确动作**：

1. **停下来** —— 不要 `checkout`、不要 `stash`、不要覆盖 ✗
2. **读 `git diff`** —— 弄清别人做到哪了
3. **看 `BACKLOG.md` 里有没有对应的 `进行中`** —— 有没有写归属
4. **两者对得上** → 你接手了 ✓ 先把它推到能提交的状态 ✓
5. **对不上** → **问** ✗ 不要猜、不要"顺手清理"

> **工作区里的未提交改动，是别人尚未说完的话。** 不要替他说完，也不要擦掉。

### 规则 4：**一个工作区同一时间只允许一个 agent**

两个 agent 同时改同一个工作区 ⇒ **必然冲突**，而且**冲突可能在无提示的情况下覆盖** ✗

**要并行就隔离**：每个 agent 一个 branch，或一个 `git worktree` ✓

## 三、交接怎么写

**交接的载体就是 `BACKLOG.md` 那一行** ✓ —— **不要另开一个 `HANDOFF.md`** ✗
（多一个文件就多一个会忘的地方 ✓ 而状态**本来就该在那**）

**一段合格的交接**，接手的人读完应该能回答：

- [ ] 这事做到哪了？
- [ ] 工作区为什么是脏的？
- [ ] 我该做的**第一个具体动作**是什么？
- [ ] 有什么已经试过但**不行**的路？（避免重走）

**最后一条最容易被漏，但最省时间** ✓ ——
**"我试过 X，不行，因为 Y"** 比"我做了 X"更有价值 ✓✓

---

## 四、会话结束时

**不要留一个不可解释的工作区。**

三选一，都要写进 `BACKLOG.md` 那一行：

| 情况 | 动作 |
|---|---|
| 做完了 | 提交 ✓ → 状态改 `已完成` ✓ → 付证据 ✓ |
| 没做完，但到了能停的地方 | **`wip:` 提交** ✓ → 状态留 `进行中` ✓ → 写**下一步** ✓ |
| 没做完，且中间状态很乱 | 提交到一个 branch ✓（哪怕叫 `wip/xxx` ✓）→ 在条目里写**去哪个 branch 找** ✓ |

**唯一不可接受的是**：把改动留在工作区里，然后离开 ✗✓

## 五、真实案例（这套规则就是因为这个加进来的）

**一个项目的实际经过**：

```
Day 0   会话 A 做了 R-008（全局异常处理），写了十项隔离测试，10/10 通过
        —— 但【没有提交】，也没有更新 BACKLOG 的进展

        BACKLOG 上写的是：  R-008 | 进行中 | 全局异常处理 | 无（…）
        —— 读起来像"有人刚开工"，看不出已经有十项测试通过了

Day 8   会话 B 接手，读 BACKLOG，判断 R-008「还在进行中」
        跑 git status 才发现工作区是脏的，有 4 个文件改了 + 一个未跟踪的测试目录
        —— 从【文件时间戳】才推测出"这是别人做的"，而不是从任何交接记录
        差一点就重新实现那十项测试
```

**两个缺口，各对应一条规则**：

| 现象 | 缺的是 |
|---|---|
| BACKLOG 写着"进行中"，但没有归属和进展 | **规则 1** |
| 做完的十项测试 8 天没进版本库，另一个 agent 看不见 | **规则 2** |

**注意**：会话 A **并没有偷懒** —— 它做完了一整套测试 ✓
**它只是没提交、没写进展** ✗ —— 而这就足够让下一个 agent 白干一遍 ✓

## 六、和四条核心判断的关系

这份文件是**第二条判断**（"完成"必须附可复现的证据）在**时间维度**上的延伸：

> 证据不只是"证明我做完了" ✓
> **它还是"下一个 agent 不必重做"的唯一依据** ✓✓
